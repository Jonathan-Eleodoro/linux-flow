Antes de usar com turmas

Quem pode consultar o progresso da turma?

Um perfil sincronizado pode criar uma sala ou grupo, mas isso não prova que pertença a um professor. Somente o criador com concessão docente ativa vê registros nominativos da sala e resultados individuais no grupo.

RecursoIntegranteCriador comumCriador aprovado
Jogar e ver placar da salaSimSimSim
Iniciar e avançar a salaNãoSimSim
Ver registro nominativoNãoNãoSim
Ver resultado do próprio perfil no grupoSimSimSim
Ver resultados individuais do grupoNãoNãoSim

A concessão técnica não verifica identidade por si só. A escola deve identificar o docente fora do aplicativo, definir quem aprova e revoga, registrar a decisão em local privado e proteger o código de acesso do perfil. Não conceda acesso a uma turma real antes dessas decisões e das regras de privacidade para menores.

Teste no banco Preview, com duas pessoas fictícias

  1. Prepare o banco isolado

    No projeto Pages, abra Settings → Bindings → Preview e confirme que DB aponta para um D1 de teste, diferente do de Production. Aplique o esquema e as migrações 001 e 002 conforme o guia de publicação. Em /api/health do Preview, espere HTTP 200 e {"status":"ready"}.

    EsperadoA tabela educator_grants existe no D1 Preview; nenhuma concessão real foi feita.
  2. Teste o acesso comum

    Em duas janelas privadas, crie os perfis fictícios Docente Teste e Aluno Teste. Com o primeiro, crie sala e grupo; com o segundo, entre usando os códigos. Faça um quiz no segundo perfil. Volte ao primeiro e abra sala e grupo.

    EsperadoO criador controla a sala, mas não vê “Registro do mestre”. No grupo vê somente seu próprio progresso, embora veja a quantidade de participantes.
  3. Conceda acesso apenas ao perfil de teste

    No D1 Preview → Console, localize o ID do perfil fictício. Confira apelido e ID antes de copiar. Troque os campos em maiúsculas no SQL abaixo pelo ID exato e pelo nome do responsável pelo teste; não use o código secreto de acesso.

    SELECT id, nickname FROM synced_profiles WHERE nickname = 'Docente Teste';
INSERT INTO educator_grants (profile_id, approved_by)
VALUES ('PROFILE_ID_CONFERIDO', 'RESPONSAVEL_PELO_TESTE');
    EsperadoUma linha de concessão ativa para o ID escolhido. Uma segunda concessão ativa para o mesmo perfil é recusada pelo banco.
  4. Confira e revogue

    Atualize a sala e o grupo no primeiro navegador. O registro e o relatório com os dois perfis devem aparecer; o segundo perfil continua sem acesso. No D1 Preview, substitua o ID e o responsável e execute a revogação abaixo. Atualize a página novamente.

    UPDATE educator_grants
SET revoked_at = strftime('%Y-%m-%dT%H:%M:%fZ', 'now'),
    revoked_by = 'RESPONSAVEL_PELO_TESTE'
WHERE profile_id = 'PROFILE_ID_CONFERIDO' AND revoked_at IS NULL;
    EsperadoRegistro e resultados dos demais desaparecem imediatamente após a nova consulta. A linha antiga permanece como histórico de concessão e revogação.
  5. Limpe o teste

    Apague os dois perfis fictícios pela tela de dados. Não transfira ID, código de perfil, logs ou respostas de estudantes para GitHub, guia público ou chat. Registre apenas se cada verificação passou e a URL do Preview.

    EsperadoOs perfis e suas concessões deixam de existir no banco de teste.
Antes de conceder em ProductionEscola confirma identidade, vínculo, finalidade e prazo. Responsável autorizado executa o SQL no banco correto.
Se o código de acesso vazarRevogue a concessão imediatamente. Crie outro perfil docente após verificar a pessoa e reveja os acessos.

O esquema registra quem aprovou e revogou, mas a autorização institucional e os detalhes da decisão devem ficar em registro privado. O acesso docente não torna quizzes com gabarito público adequados a notas oficiais.
