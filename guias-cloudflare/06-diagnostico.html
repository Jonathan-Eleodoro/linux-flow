Valores para conferir no painel

Tipo: Pages (Git integration)
Repositório: Jonathan-Eleodoro/linux-flow
Root directory: vazio / raiz
Framework: None
Build command: npm run build
Build output directory: dist
Deploy command de Worker: nenhum
Functions directory: functions/ na raiz
D1 binding: DB (após criar o banco)

Se a aplicação atual for do tipo Worker, não tente consertá-la apenas alterando o diretório de saída. Crie um projeto Pages conectado ao mesmo repositório e teste-o antes de apontar um domínio próprio. O nome exato do projeto pode precisar ser diferente se linux-flow já estiver em uso.

Orientações da conversa que não devem ser aplicadas

  • Não use .pagesignore para esconder functions/. Essa pasta fornece as APIs de perfil, ranking, grupos e Premium.
  • Não renomeie functions/ para backup. O site poderia abrir, mas o backend desapareceria.
  • Não aponte Root directory para dist e output para .. O build começa antes de dist existir.
  • Não use Build watch paths para excluir node_modules/; isso só controla disparos de build.
  • Não crie wrangler.jsonc incompleto com pages_build_output_dir enquanto os bindings D1 forem geridos no painel; o arquivo passa a ser a fonte de configuração de produção.
Atualização de 01/10: um novo wrangler.jsonc foi incluído no GitHub com nome, data e flag de compatibilidade. Ele foi convertido para UTF-8, mas não contém pages_build_output_dir nem binding D1. Portanto, não prova que Pages ou o banco já foram publicados.

Depois da correção

Faça um novo deploy a partir do commit atualizado. Um “Retry” do commit antigo reutiliza o código antigo. No log, procure Build command completed, publicação dos assets de dist e publicação das Functions sem erros. Só então teste /api/ranking?category=all&level=1&total=10. Um 503 posterior aponta para binding DB ou esquema D1, não para o frontend.

A conversa com outra IA é evidência dos passos tentados, não instrução obrigatória. Este guia segue a arquitetura real do repositório.
